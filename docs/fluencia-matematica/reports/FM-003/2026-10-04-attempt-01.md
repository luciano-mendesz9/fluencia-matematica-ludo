  8.22.0. O Prisma Client é gerado em `src/generated/prisma` no `postinstall` e não é versionado.

  E-mail normalizado, código de aluno e hash de sessão possuem unicidade; tokens e senhas só têm
  campos para hash, nunca valor puro.
- `src/lib/prisma.ts` é a única instância, marcada como server-only, com singleton em desenvolvimento,
  adapter Neon e `DATABASE_URL` pooled.
- `prisma.config.ts` usa `DIRECT_URL` quando disponível. Um endereço local inerte permite somente
  validar schema e gerar client sem credenciais; comandos de rede passam pelo wrapper protegido.
- `.env.example` documenta apenas placeholders e nenhuma variável é pública para o navegador.

## Regras e validação no servidor

O guard exige um dos três IDs explicitamente permitidos (development/test/E2E), host Neon, URL de
runtime pooled, URL CLI direta e igualdade de endpoint/banco lógico. Produção, host não Neon, destino
divergente, variável ausente ou marker diferente são recusados sem imprimir URL ou credencial.

Antes de `migrate dev`, `migrate status` ou `migrate deploy`, `scripts/prisma-safe.ts` conecta pela URL
direta e compara `APP_ENV_ID` com `current_setting('app.environment_id', true)`. O marker precisa ser
provisionado pelo responsável na branch Neon isolada; não há bypass por `NODE_ENV`.

## Schema/migrations e destino

A migration `20261004184500_foundation` cria a história PostgreSQL mínima de identidade, sessão e
auditoria, com UUID, `timestamptz`, JSONB, índices e FKs. O SQL foi reproduzido por `prisma migrate
diff --from-empty` sem diferença. Nenhum SQLite, `db push`, reset, seed ou conexão de produção foi usado.

Não foi possível executar `migrate status/deploy`, aplicar a migration em banco vazio, verificar
unicidades/rollback no PostgreSQL ou testar conexão real: as três variáveis obrigatórias estão ausentes.
Esse skip não aprova o gate de banco.
